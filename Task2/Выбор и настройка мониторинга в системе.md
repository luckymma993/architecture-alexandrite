# Выбор и настройка мониторинга в системе

## Мотивация

Сейчас в системе «Александрит» нет мониторинга. Об инцидентах компания узнаёт от клиентов: API users сообщают о пропавших заказах, операторы — о медленной главной странице MES, покупатели — о сроках в несколько месяцев. Команда не может ответить на базовые вопросы:

- какая из систем (Shop, CRM, MES) не справляется с нагрузкой;
- в каком статусе копятся заказы и сколько времени они там проводят;
- теряются ли сообщения в RabbitMQ и в каком количестве;
- хватит ли ресурсов при росте на 100 заказов в месяц.

Мониторинг нужен, чтобы:

1. **Видеть проблему раньше клиента.** Алерт на рост ошибок или очереди приходит дежурному, а не в виде жалобы.
2. **Находить узкие места по данным.** Например, подтвердить, что заказы застревают в SUBMITTED из-за расчёта цены, а не в CRM.
3. **Измерять эффект изменений.** Каждая инициатива плана (асинхронный расчёт, кеш, надёжная интеграция) получает метрику «до» и «после».
4. **Планировать мощности.** Тренды CPU, памяти, размера БД и S3 показывают, когда понадобится масштабирование.

Это прямо влияет на бизнес: меньше потерянных заказов, быстрее выполнение, вернуть доверие B2B-клиентов.

## Выбор подхода к мониторингу

Используется комбинация трёх подходов: разные части системы требуют разного взгляда.

| Часть системы | Подход | Почему |
|---|---|---|
| Shop API, CRM API, MES API | **RED** (Rate, Errors, Duration) | Это сервисы, которые обрабатывают запросы. Для них главное — сколько запросов, сколько ошибок, как быстро отвечают. RED напрямую показывает то, что чувствует пользователь |
| Инстансы приложений, Shop DB, MES DB, S3 | **USE** (Utilization, Saturation, Errors) | Это ресурсы. Для них важно, насколько они загружены, есть ли очередь ожидания и ошибки. USE отвечает на вопрос «хватает ли ресурсов» |
| RabbitMQ | **USE** + специфичные метрики очереди | Очередь — ресурс между системами: её насыщение — это длина очереди и сообщения в DLX |
| Система целиком, точки входа пользователей | **Четыре золотых сигнала** (Latency, Traffic, Errors, Saturation) | Общий дашборд для руководства и дежурного: одним взглядом видно состояние всей системы |
| Процесс заказа | **Бизнес-метрики** | Технические метрики не показывают, что заказ «завис». Нужны количество заказов по статусам и время в каждом статусе |

## Метрики

Метрики из предложенного списка оценены по принципу «помогает ли она принять решение». Для каждой указаны нужность, обоснование и ярлыки (labels). Ярлыки выбраны с низкой кардинальностью: без order_id и user_id в метриках, иначе Prometheus быстро переполнится. Идентификаторы заказов ищутся в логах и трейсах.

### Метрики из предложенного списка

| Метрика | Нужна | Почему | Ярлыки |
|---|---|---|---|
| Number of dead-letter-exchange letters in RabbitMQ | **Да, критично** | Сообщения в DLX — это заказы и смены статусов, которые не удалось обработать. Прямой индикатор потери заказов, на которые жалуются API users | `queue`, `vhost`, `reason` (rejected, expired, maxlen), `env` |
| Number of message in flight in RabbitMQ | **Да** | Рост неподтверждённых и ожидающих сообщений показывает, что потребитель (CRM API или MES API) не успевает. Ранний сигнал перед потерями | `queue`, `vhost`, `consumer_service`, `env` |
| Number of requests (RPS) for internet shop API | **Да** | Rate в RED. Показывает нагрузку от покупателей, нужен для планирования мощностей | `service`, `method`, `route`, `status_class`, `env` |
| Number of requests (RPS) for CRM API | **Да** | Rate в RED для CRM | `service`, `method`, `route`, `status_class`, `env` |
| Number of requests (RPS) for MES API | **Да, критично** | Нагрузка от операторов и API users на MES. Позволяет увидеть всплески от конкретного клиента API | `service`, `method`, `route`, `status_class`, `client_type` (operator, api_user), `api_client` (только для API users, их немного), `env` |
| Number of requests (RPS) per user for internet shop API | **Нет** | Пользователей тысячи, метрика с `user_id` создаёт огромную кардинальность. Подозрительные пользователи ищутся по логам | — |
| Number of requests (RPS) per user for CRM API | **Нет** | Продавцов мало, их активность не влияет на проблемы. Достаточно общего RPS | — |
| Number of requests (RPS) per user for MES API | **Частично** | По операторам — не нужно. По API users — нужно для квот и поиска клиента, перегружающего систему. Реализуется ярлыком `api_client` в метрике RPS MES API, отдельная метрика не нужна | `api_client` |
| CPU % for shop API | **Да** | Utilization в USE для инстанса Shop API | `service`, `instance`, `env` |
| CPU % for CRM API | **Да** | Utilization для CRM API | `service`, `instance`, `env` |
| CPU % for MES API | **Да, критично** | Расчёт цены нагружает CPU MES API. Основной сигнал перегрузки при потоке заказов | `service`, `instance`, `env` |
| Memory Utilisation for shop API | **Да** | Утечки памяти и OOM в JVM | `service`, `instance`, `area` (heap, non_heap), `env` |
| Memory Utilisation for CRM API | **Да** | То же для CRM | `service`, `instance`, `area`, `env` |
| Memory Utilisation for MES API | **Да** | Расчёт сложных моделей потребляет много памяти | `service`, `instance`, `env` |
| Memory Utilisation for shop db instance | **Да** | Нехватка памяти БД ведёт к чтению с диска и медленным запросам | `db`, `instance`, `env` |
| Memory Utilisation for MES db instance | **Да** | Связано с медленной главной страницей MES | `db`, `instance`, `env` |
| Number of connections for shop db instance | **Да** | Исчерпание пула соединений — частая причина ошибок 500. Shop DB используют два сервиса | `db`, `instance`, `client_service`, `state` (active, idle), `env` |
| Number of connections for MES db instance | **Да** | То же для MES DB, особенно при долгих расчётах | `db`, `instance`, `client_service`, `state`, `env` |
| Response time (latency) for shop API | **Да** | Duration в RED. Перцентили p50, p95, p99, а не среднее | `service`, `method`, `route`, `env` (гистограмма) |
| Response time (latency) for CRM API | **Да** | Duration для CRM | `service`, `method`, `route`, `env` |
| Response time (latency) for MES API | **Да, критично** | Медленная главная страница операторов — это latency маршрута списка заказов | `service`, `method`, `route`, `client_type`, `env` |
| Size of S3 storage | **Да** | Рост затрат и планирование. 3D-модели занимают много места | `bucket`, `env` |
| Size of shop db instance | **Да** | Планирование диска, предотвращение переполнения | `db`, `env` |
| Size of MES db instance | **Да** | То же для MES DB | `db`, `env` |
| Number of HTTP 200 for shop API | **Да, в составе общей метрики** | Отдельная метрика не нужна: это часть счётчика запросов с ярлыком статуса. Нужна для расчёта доли успешных запросов | `service`, `route`, `status_code`, `env` |
| Number of HTTP 200 for CRM API | **Да, в составе общей метрики** | То же | `service`, `route`, `status_code`, `env` |
| Number of HTTP 200 for MES API | **Да, в составе общей метрики** | То же | `service`, `route`, `status_code`, `client_type`, `env` |
| Number of HTTP 500 for shop API | **Да** | Errors в RED. Ошибки сервера при оформлении заказа — потерянные продажи | `service`, `route`, `status_code`, `env` |
| Number of HTTP 500 for CRM API | **Да** | Errors для CRM | `service`, `route`, `status_code`, `env` |
| Number of HTTP 500 for MES API | **Да, критично** | Ошибки при создании заказа через API — одна из причин «потерянных» заказов | `service`, `route`, `status_code`, `client_type`, `api_client`, `env` |
| Number of simultaneous sessions for shop API | **Частично** | Полезно для маркетинга и планирования нагрузки в пиковые дни, но для поиска проблем достаточно RPS | `service`, `env` |
| Number of simultaneous sessions for CRM API | **Нет** | Продавцов мало, метрика ничего не добавит | — |
| Number of simultaneous sessions for MES API | **Нет** | Операторов мало, важнее latency их запросов | — |
| Kb transferred (received) for shop API | **Частично** | Нужна для загрузки 3D-моделей: большие файлы влияют на время ответа. Для остальных маршрутов не нужна | `service`, `route`, `env` |
| Kb transferred (received) for CRM API | **Нет** | Нет больших входящих данных | — |
| Kb transferred (received) for MES API | **Частично** | API users передают модели для расчёта, объём влияет на нагрузку | `service`, `route`, `api_client`, `env` |
| Kb transferred (sent) for shop API | **Нет** | Не помогает в принятии решений | — |
| Kb transferred (sent) for CRM API | **Нет** | Не помогает в принятии решений | — |
| Kb transferred (sent) for MES API | **Частично** | Размер ответа списка заказов. Если он большой, страница грузится медленно из-за выдачи, а не БД | `service`, `route`, `env` |

### Дополнительные метрики

| Метрика | Почему | Ярлыки |
|---|---|---|
| Количество заказов в каждом статусе | Показывает, где копятся заказы. Рост SUBMITTED — проблема расчёта цены, рост PRICE_CALCULATED — продавцы не успевают подтверждать | `status`, `source` (shop, api), `env` |
| Время нахождения заказа в статусе (гистограмма) | Главная бизнес-метрика: соответствует жалобам «заказ выполняется месяцами» | `status`, `source`, `env` |
| Длительность расчёта цены (гистограмма) | Расчёт длится от 2 до 30 минут. Нужно видеть распределение и планировать число воркеров | `complexity` (simple, complex), `env` |
| Очередь заказов на расчёт цены | Saturation MES: сколько заказов ждут расчёта | `env` |
| Заказы от API users, не появившиеся в CRM за N минут | Прямой индикатор потери заказа при интеграции | `api_client`, `env` |
| Время выполнения запросов к БД (p95, p99) и медленные запросы | Связано с медленной страницей MES | `db`, `query_type`, `env` |
| Ошибки и повторы обработки сообщений RabbitMQ | Сколько раз потребитель не смог обработать сообщение | `queue`, `consumer_service`, `env` |
| Публикации без подтверждения от RabbitMQ | Сообщения, которые могли не дойти до брокера | `exchange`, `publisher_service`, `env` |
| Доступность (up) каждого сервиса | Простейший сигнал «сервис не отвечает» | `service`, `instance`, `env` |
| Использование диска инстансов | Saturation в USE, локальные логи могут переполнить диск | `service`, `instance`, `mountpoint`, `env` |

## Пороги насыщения и действия

| Ресурс | Метрика | Предупреждение | Критично | Что делать |
|---|---|---|---|---|
| RabbitMQ DLX | Сообщения в DLX | > 0 за 5 минут | > 10 за 5 минут | Дежурный разбирает сообщения по логам и трейсам, переотправляет после исправления причины |
| RabbitMQ | Сообщений в очереди / in flight | > 1000 в течение 10 минут | > 5000 или рост 30 минут подряд | Проверить потребителя, увеличить число потребителей, при необходимости масштабировать CRM API / MES API |
| MES API | CPU | > 70% 15 минут | > 90% 5 минут | Ограничить RPS API users на шлюзе, добавить инстанс или воркеры расчёта |
| Любой API | Память | > 75% | > 90% | Проверить утечку, перезапустить, увеличить память инстанса |
| Любой API | Доля HTTP 5xx | > 1% за 5 минут | > 5% за 5 минут | Посмотреть логи и трейсы, откатить релиз при связи с ним |
| MES API | p95 latency списка заказов | > 1 с | > 3 с | Проверить медленные запросы и кеш, нагрузку на MES DB |
| Shop API / CRM API | p95 latency | > 500 мс | > 2 с | Проверить БД и внешние вызовы |
| Shop DB, MES DB | Соединения от максимума пула | > 70% | > 90% | Найти долгие транзакции, настроить пул, рассмотреть PgBouncer |
| Shop DB, MES DB | Память / CPU | > 75% | > 90% | Оптимизировать запросы, увеличить класс инстанса, вынести чтение на реплику |
| Shop DB, MES DB, S3 | Занятое место | > 70% | > 85% | Увеличить диск, настроить архивирование старых данных |
| Процесс заказа | Время в SUBMITTED | p95 > 1 ч | p95 > 4 ч | Проверить очередь расчёта, добавить воркеры |
| Процесс заказа | Заказ API user не появился в CRM | — | > 5 минут | Найти заказ по трейсу, восстановить вручную, исправить причину |

Предупреждения уходят в рабочий чат команды, критичные алерты — дежурному в Telegram и на почту.

## План действий

1. **Выбрать и развернуть стек.** Prometheus для сбора, Grafana для дашбордов, Alertmanager для алертов. Развернуть в Yandex Cloud отдельно от продуктовых инстансов. Для managed-сервисов (PostgreSQL, S3) подключить Yandex Monitoring как источник данных в Grafana.
2. **Подключить инфраструктурные экспортёры:** node_exporter на инстансы приложений, встроенный Prometheus-плагин RabbitMQ, метрики managed PostgreSQL и Object Storage.
3. **Инструментировать приложения.** Shop API и CRM API: Spring Boot Actuator + Micrometer (`/actuator/prometheus`). MES API: prometheus-net для .NET. Добавить гистограммы latency и счётчики запросов с ярлыками из таблицы.
4. **Добавить бизнес-метрики:** счётчики смены статусов заказа, гистограммы времени в статусе и длительности расчёта цены.
5. **Собрать дашборды:**
   - обзор системы по четырём золотым сигналам;
   - RED по каждому API;
   - USE по инстансам, БД и RabbitMQ;
   - воронка заказов по статусам.
6. **Настроить алерты** по таблице порогов, маршрутизацию по важности в Alertmanager, дежурства.
7. **Задокументировать runbook:** для каждого алерта — что проверить и что сделать.
8. **Определить SLO** на основе собранных за месяц данных. Например, 99,5% запросов MES API быстрее 1 с, 100% заказов API users создаются в CRM за 5 минут.
9. **Раз в квартал пересматривать** метрики, пороги и алерты: убирать шумные, добавлять недостающие.
